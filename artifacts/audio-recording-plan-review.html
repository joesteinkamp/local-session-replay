Audio recording plan — improvement review

Source: audio-recording-plan.md · Reviewed against src/core/*, export, player, package.json · 2026-10-07 · Lenses: technical architect, product/UX, adversarial refuter (Codex cross-vendor pass hung on hooks; skipped)

Verdict: The plan’s diagnosis is strong — failure taxonomy, keep visual recording, honest gaps, and distrust of “code exists ⇒ reliable” are right. It is not yet ready to implement as written. Before coding recovery UI, resolve the enabled/stopAsking model, status vocabulary, and what “live” means; defer or narrow track-mute and irreversible seq-trim; rewrite sync acceptance so AEC does not poison the gate; and treat Baseline as greenfield (no test:browser today).

What already works in the plan

  • Three failure classes with visual recording continuing — matches the real split in audio.js / session.js.
  • Overlay and player sharing audioGaps for saved-audio status is the right single source of truth (with caveats on inputs/thresholds below).
  • Honest about fake-device limits and Safari needing real hardware; delivery order (baseline → recovery → matrix) is the right shape.

Priority findings

P0

Fix enabled vs stop-asking before any Retry UI

schema

Plan §2 correctly names the bug: persistent denial sets session.audio.enabled = false, which makes audioGaps return nothing and summary say “Audio: not recorded” even when segments exist (session.js ~419, summary.js). Reusing resume() / restartAudioAfterNavigation without a schema split will ship Recovery that re-triggers the bug.

Decide fields, write rules at start / denial / skip / retry, and one CONTRACTS meaning for “not recorded” vs “recorded with gaps.” Base reporting on persisted segments.

P0

Blocked vs recoverable “Unavailable” must be different UX

product

§2 collapses device loss, recorder error, persistence failure, and later-page denial into one “Audio isn't recording” + Retry. Denial needs site-settings guidance and stop-asking; device loss needs Retry / devicechange offer. Testers will not know whether to open settings or click Retry.

Split copy/CTAs: Microphone blocked vs Audio stopped (recoverable). Do not auto-getUserMedia on devicechange.

P0

Define when status becomes live

correctness

Acceptance requires “badge never shows live while nothing is saved,” but appendAudio failures only hit reportError today — audio status can stay live (session.js onChunk). Track mute can still append silent chunks successfully, so silence ≠ unsaved.

Pick the signal: after first successful appendAudio, or demote on write failure / stop segment. Narrow acceptance: never Recording when the active segment is not appending (Mute excepted).

P0

Sync acceptance methodology fights AEC

acceptance

Speaker beep → mic + on-screen counter assumes loopback. Capture requests echoCancellation: true (audio.js ~119). AEC often removes speaker audio from the mic path — the gate can fail a good player or pass a bad one.

Use a fixture that does not rely on speaker→mic (injected tick / AEC off for the harness), or mark headphone-only as N/A. Align the 500 ms proposal with player’s existing 300 ms DRIFT_TOLERANCE_S.

P1

Coverage clock ≠ media duration

architecture

groupAudioChunks uses last chunk wall ts as endTs; the player seeks by wall elapsed. MediaRecorder dataavailable timing is not media duration (plan cites MDN). Seq-gap trimming that shortens endTs inherits the same lie.

Long-term: derive playable length from decoded/blob duration. Short-term: do not treat gap-trim unit tests or marker sync alone as reliability proof.

P1

Baseline cites tooling that does not exist

delivery

Delivery step 1: “e.g. npm run test:browser.” package.json only has test / build / serve — no Playwright/Puppeteer harness. Baseline is greenfield, not wiring existing tests.

Make harness existence part of Baseline done-when; put one Safari real-mic smoke and offline seek/decode before Recovery is “done.”

P1

“Reuse resume/navigation” under-specifies a shared primitive

implementation

Those paths differ in gap accounting and whether they persist enabled: false. onProblem does not await stopSegment(). “Wait for failed segment to settle” is new coordination, not reuse.

Plan should name one retryMic-style controller surface and its interaction with generation.

P1

Seq-gap trim is irreversible and still an open question

export

Plan admits unknown browser decode of stitched segments with missing chunks, then plans to cut at first seq hole in grouping. That can permanently discard data that might still decode.

Prefer detect + surface (“unreliable segment”) until the matrix records decode behavior; missing seq 0 → drop segment is the safer first cut.

P1

Track mute as a first-class failure oversells browsers

devices

Code only listens for ended + recorder error. Plan’s own open question: browsers may fire mute vs ended. A silent track can still save chunks; acceptance equating mute with “nothing saved” is wrong.

Ship ended, recorder error, and appendAudio failure with status≠live first; treat mute/devicechange as observational until the matrix says otherwise.

P1

Internal contradiction: pause releases mic

accuracy

“Already in place” says a paused page releases the microphone. §3 says pause does not necessarily release the stream. Code: same-page pause() only stopSegment(); release is on paused navigation/bfcache restore.

Fix the “already in place” bullet; add user-facing pause copy that the browser mic indicator may remain until Stop/Discard.

P1

“Audio recorded with gaps” needs a user threshold

product

audioGaps already drops gaps < 500 ms, but short nav gaps and seq-trims will often produce some gap. Without explicit “with gaps” rules and copy (“gaps = missing capture, not bad speech”), download will cry wolf.

P2

Consent when audio intent changes

product

Keeping Continue-without-audio after a passed check is good, but the plan never says whether skip-after-pass or mid-session Retry needs re-consent. Add an explicit rule.

P2

Collapsed bubble / tab ownership / sleep

edge cases

Recovery must be obvious when the panel is collapsed (aria-live / badge). Also missing: Retry while paused or in Stop dialog; another tab owns recording; laptop sleep ending tracks; SPA routes that never hit restartAudioAfterNavigation.

P2

Quota vs export size

ops

60‑minute AC mentions storage quota but not HTML/base64 export memory. Recording can fit IDB while export OOMs. State a supported max and the exact failure string for both paths.

Suggested plan rewrites

Status dictionary (replace §3 prose) 
User-facing audio status is exactly one of:
  Microphone on | Muted | Paused (session phase; mic badge secondary) |
  Reconnecting… | Microphone blocked | Audio stopped (recoverable).

Download line (stopped view, before Download) is exactly one of:
  Audio recorded | Audio recorded with gaps (uncovered ≥ AUDIO_GAP_MIN_MS
  outside pause spans) | No audio recorded.

Overlay, summary, and player gap list must use the same audioGaps result
on the same post-grouping segments.
Recovery CTAs (replace §2 one-liner) 
Recoverable failure: “Audio stopped — screen is still recording.” Primary: Retry microphone.
Blocked permission: “Microphone blocked — screen is still recording.”
  Primary: How to allow microphone. Secondary: Continue without microphone (stop-asking; keep segments).
Do not auto-call getUserMedia on devicechange; only emphasize Retry when a device reappears.
Announce via the existing live region when the panel is collapsed.
Delivery order (replace § Delivery) 
0. Schema: enabled vs stopAsking vs has-segments; CONTRACTS updated.
1. Baseline harness: real test:browser (or equivalent) with Chrome fake audio;
   record → navigate ×2 → export → assert segments + gaps + decode/seek smoke.
2. Capture/status: ended, recorder error, appendAudio→status≠live; Retry primitive;
   unit tests. Seq continuity: detect/report; trim only after matrix evidence.
3. Acceptance matrix: real mic, disconnect, Safari; sync fixture without AEC poison;
   commit results. Mute/devicechange policies filled from observations.
Open disagreement (leave for your call): Architect/refuter lean toward media-duration as coverage truth and soft seq-gap handling first. The plan’s hard trim-at-first-hole is simpler to implement and may be fine if you accept permanent discard of trailing chunks. Recommendation: detect in Baseline, decide trim vs soft after one Chrome+Firefox+Safari decode pass — don’t lock the cut rule in §5 yet.
