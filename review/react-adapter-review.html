What to fix in the plan

These are proposal omissions and ambiguities, not claims that an implemented adapter already fails. Resolve P1 before implementation and P2 before handoff.

P1 · 1

Explicitly externalize React in the package build

Plan 25, 80–81 · scripts/build.mjs:16–25, 63–71

The plan says “do not bundle React,” but peers alone do not achieve that. The current esbuild configuration uses bundle:true with no externals. Adding useEffect can embed a different React instance from the host renderer, causing hook failures.

Add: external: ['react', 'react-dom'] to the package ESM build; package externals cover subpaths too. Keep rrweb/player bundled into the lazy core. Do not externalize every dependency indiscriminately: rrweb and rrweb-player currently exist only as build-time dev dependencies.

Prove: inspect the output/build graph for external React imports and no embedded React runtime; render the installed package with the host’s React 18 and 19.

esbuild external configuration · React duplicate-runtime explanation

P2 · 2

Define page lifetime and unmount behavior

Plan 23, 70–73, 97 · src/core/index.js:8–19; src/core/session.js:583–644

The core discards the overlay destroy handle and exposes no controller disposal method. A thin component wrapper therefore leaves recording and overlay alive after unmount; a pending boot may finish after the component disappears.

Recommendation: explicitly preserve a page-lifetime bootstrap in v1. Unmount does not disable it; keep it at the stable app root, use the overlay to stop capture, and reload to change configuration. If unmount must stop capture, expand scope to ownership, async cancellation and full resource disposal.

Do not add overlay-only cleanup mechanically. StrictMode repeats effect setup/cleanup, while the global claim suppresses a second boot; cleanup could remove the first overlay permanently. Missing cleanup is not inherently a bug under a documented page-lifetime contract. React effect lifecycle.

P2 · 3

First props means first attempt across the whole page

Plan 23, 34, 72, 97 · src/index.js:9–12; src/activation.js:13–16, 32–46

The global claim occurs before activation and is shared with script installs. Mounting inactive consumes it. Later active mounts, changed keys, asynchronous task data, another study, and client-side query changes do not re-evaluate initialization.

Add: “The first committed mount attempt on the page owns initial configuration, even when inactive. Wait to mount until study/tasks are ready; later props and remounts do not reconfigure it. Reload to change configuration.” Preserve the locked behavior unless deliberately reopening that decision.

Require useful diagnostics for conflicting later instances, without warning on every new object identity: the sample’s inline tasks array changes identity on parent renders. Document existing precedence: initial ?test=0 wins; otherwise a fresh session precedes activate=false. An activation predicate is not an authorization boundary.

P2 · 4

Catch asynchronous boot failures at the component boundary

Plan 70, 79, 130 · src/index.js:12; src/core/index.js:10–15, 23

The dynamic import can reject before the core catch exists. Calling boot from an effect without handling its promise can emit an unhandled rejection when a chunk fails to load. Consumers no longer receive an init() promise to await. Both initialization guards also remain set after failures.

Add: a synchronous effect callback that launches boot with explicit rejection handling, consistent diagnostics for chunk/storage failures, and a recovery policy. “Fix the cause and reload” is sufficient for v1. Do not clear guards and retry partially initialized resources without cleanup.

Test rejected imports and storage boot failure. Permanent failure flags are inherited behavior; containing a fire-and-forget launch is an adapter integration responsibility.

P2 · 5

Separate SSR safety from Server Component support

Plan 70–73, 80 · scripts/build.mjs:63–71; README.md:16–39

A window guard protects runtime boot; it does not create a client boundary for a hook-using module imported from a Server Component. The current README names Next as a supported host. A Vite-only example cannot establish that path.

Add: preserve 'use client' in the shipped component entry and test the built package in an RSC consumer, or explicitly require and demonstrate a host client wrapper. A source directive alone is not enough if bundling strips it. Separately test ordinary SSR and hydration without server-side browser-global access.

Function-valued activate must be defined inside client code; ordinary callbacks cannot cross the server/client boundary. This finding does not claim ordinary SSR is broken. Next library-author guidance · React serialization rules.

P2 · 6

Validate the delivered package, not only a linked example

Plan 80, 91–99, 123–126 · package.json:7–27; test/index.test.js:7–27

Current entry tests import source directly. A linked example can inherit repository dependencies or resolve a second React. Neither proves packaged exports, copied types, emitted chunks, or a clean install.

Add: install a built tarball into an isolated consumer; import only the package name; run a production build and complete session/export. Also test the documented Git install from a pinned commit, since prepare is a separate delivery path. Exercise both React majors and compile a TSX consumer against shipped declarations.

Qualify line 80: the host app bundler does not repeat the CSS/player build, but a Git install runs TestKit’s own prepare build. Document supported Node/package-manager versions and lifecycle-script requirements. npm lifecycle documentation.

P2 · 7

Plan the breaking migration and keep the script init example

Plan 18, 77–87, 119 · src/loader.js:13–27; src/index.js:10; package.json:3

Removing the advertised named init export from a 1.0.0 package is intentionally breaking. Specify release/version policy and a before/after migration, including what happens to non-React bundled consumers. This does not require reopening the locked React-only API decision.

“init is not … in README” directly conflicts with keeping script installs: those still need window.TestKit.init(). Scope the removal to the named npm export and primary React examples. Extracting today’s body also preserves a browser-global init; “internal” cannot mean inaccessible everywhere.

If bumping the major, address Pages coupling: the build derives /v<major>/ from the package version and deployment replaces the site. Preserve existing script URLs or explicitly decouple script and npm versioning.

Small additions that make this implementable

  1. Lifetime: first committed attempt wins across the page, even if inactive. Unmount and new props do not stop or reconfigure capture. Reload resets configuration.
  2. Boot: one in-flight launch, complete async error containment, useful diagnostics, documented reload recovery.
  3. Build: external React, lazy bundled core, correct shipped client boundary and types, no special host build plugins.
  4. Compatibility: npm migration/version decision, script-global exception, documented SSR/RSC placement.
  5. Proof: real React rendering and clean packaged-consumer tests alongside the current suite and HTML demo.

Suggested sequence: settle lifetime/release contracts → establish package external/client-boundary checks → extract boot and add wrapper → prove production consumer behavior → finish examples/docs. Build acceptance checks alongside implementation instead of leaving all tests to step 6.

Optional improvements

  • Keep Shadow DOM and the export unchanged. No controller hook, portal rewrite, dual packages or generic disposal framework is necessary for page lifetime.
  • Justify react-dom as a peer: the wrapper only imports React. It can communicate a supported renderer constraint, or live in the example/test harness. This is dependency policy, not a blocker.
  • Expose TestKitProps from the current config; a declaration returning null avoids unnecessary global JSX namespace coupling. Check both supported type ecosystems.
  • Measure inactive production loading cost. Dynamic import defers the core; it does not promise zero wrapper bytes or prevent every host from preloading. Recheck the README’s existing ~1 KB claim.
  • Explain the sample’s -D assumption: dev dependencies must be available during the app build; production output must include the runtime code it needs.
  • Update CONTRACTS.md beyond ownership: scope “no framework” to the core and describe host-served lazy chunks in the network-loading exception.

# Plan: Agentation-style React install

**Status:** Agreed (grill-me, 2026-10-07)
**Branch / worktree:** `ai/cursor` → `../local-session-replay-cursor`
**Supersedes (narrative):** `testkit-plan.md` Phase 6 framing TestKit as its own Pages project, and the "Later → Optional React adapter" bullet as a thin afterthought.

## Problem

The original plan treated TestKit as a **separate hosted script** (own GitLab/GitHub Pages project) that prototypes load with `<script src="…/testkit.js">`. The desired model is **Agentation / DialKit-style**: install the package into the app under test, mount a React component, and let the host bundler own the code.

The repo already supports `npm i` from GitHub and `import { init } from 'local-session-replay'` with a dynamic import of the recorder. What's missing is the **React component as the public API** and making **in-app install the primary story**.

## Decisions (locked)

| Topic | Choice |
| :-- | :-- |
| Public API | `<TestKit />` only — no controller/state hook in v1 |
| `init()` | Becomes **internal**; not part of the public export / docs |
| Install model | npm into the host app (like Agentation), not a remote toolkit host |
| Package shape | **Single package**; React component is the public API |
| Core loading | Keep today's **dynamic `import()`** of core so the host splits a chunk; casual viewers who never mount/activate don't pay for rrweb |
| Script-tag / Pages | **Secondary** for plain HTML multi-page demos; keep working, demote in docs |
| Config lifecycle | **Mount-once**; first props win; ignore later prop updates |
| Example | README + **`examples/react/`** Vite app; keep HTML `demo/` for script-tag |
| React | `peerDependencies`: `react` and `react-dom` `^18.0.0 \|\| ^19.0.0` (do not bundle React) |

### Rejected alternatives

- Controller `useTestKit()` hook — not needed until apps drive session UI/flow themselves.
- Remote loader / required `src` URL — wrong distribution model for React apps.
- Bundling core into the main chunk with no split — taxes every visitor; dynamic import already matches Agentation install while preserving cost.
- Dual packages (`@testkit/core` + `@testkit/react`) — extra moving parts for one consumer shape.
- Removing script-tag / Pages entirely — still useful for no-bundler HTML prototypes.
- Re-init on prop changes — unsafe mid-session; mount-once matches today's `claimInit`.
- Replacing HTML `demo/` with React only — keep both paths proven.

## Goal

A React app can:

```sh
npm i -D github:joesteinkamp/local-session-replay
```

```jsx
import { TestKit } from 'local-session-replay';

export default function App() {
  return (
    <>
      <YourPrototype />
      <TestKit
        study="grid-filters-v2"
        tasks={[
          { id: 'filter', prompt: 'Filter to healthcare companies' },
        ]}
      />
    </>
  );
}
```

Open with `?test=1` (or a custom `activate` prop), run the session, download the same self-contained HTML export. No separate TestKit Pages project required for this path.

## Scope

### 1. `<TestKit />` component

- Props = current `TestKitConfig` (`study`, `tasks`, `activate`, `audio`, `mask`, and the rest of the config reference).
- Client-only: `useEffect` calls internal boot once; component renders `null` (overlay remains Shadow DOM).
- Respect existing activation (`?test=1`, `?test=0`, fresh in-progress session, `activate` function/boolean).
- Stable placement at the app root; ignore prop updates after mount (optional `console.warn` in development).
- SSR-safe: no-op when `typeof window === 'undefined'` (same guard as today's package entry).

### 2. Package surface

- Public export: `{ TestKit, version }` (plus TypeScript types).
- `init` is not exported from the package entry, `.d.ts`, or README.
- Internal boot module holds today's `init()` logic for the component and, if needed, the script-tag path's shared activation/boot helpers.
- Build emits the compiled component into `dist/` via existing `prepare` / `scripts/build.mjs` (host does **not** re-run TestKit's CSS/player bundling steps).
- Add `react` / `react-dom` peerDependencies as above.

### 3. Docs and plan correction

- **README:** Agentation-style `npm i` + `<TestKit />` first; script-tag + Pages under "also supported."
- **`testkit-plan.md`:** Phase 6 / Later — distribution is **in-app npm**; React component is the primary integration, not an optional afterthought. Pages is a secondary distribution for HTML-only hosts.
- **`docs/CONTRACTS.md`:** layout/ownership for the React entry; public export contract; note `init` is internal.

### 4. `examples/react/`

- Minimal Vite + React app depending on the local package (workspace / `file:` / relative install).
- Mount `<TestKit study tasks … />` beside a tiny prototype UI.
- Documented run path (e.g. `npm run example:react` or `cd examples/react && npm i && npm run dev`).

### 5. Tests

- Component wrapper: boots once; second mount no-ops; safe without `window`.
- Prefer the smallest harness that fits the repo (`node:test` if viable; otherwise a focused runner only where needed).
- Existing core/unit tests and HTML `demo/` / script-tag path remain green.

## Out of scope

- Controller / session-state React hook
- Removing GitHub Pages or the script-tag loader
- Publishing to the npm registry (stay on GitHub install unless decided later)
- In-session flagging, Whisper transcription, React-specific annotate APIs

## Implementation sketch

```
src/react/TestKit.jsx    # public component
src/boot.js              # today's init() body; not exported
src/index.js             # export { TestKit, version }
src/index.d.ts           # TestKit props + version
examples/react/          # Vite + React proof app
scripts/build.mjs        # emit React entry into dist/
```

Script-tag loader (`src/loader.js` → `public/v1/testkit.js`) keeps using internal `start` / `__TestKitCore` unchanged.

## Done when

1. A React app installs the package and uses **only** `<TestKit … />` (no public `init`).
2. `examples/react/` can run a full session with `?test=1`.
3. README, `testkit-plan.md`, and `docs/CONTRACTS.md` describe in-app install as primary.
4. Existing unit tests pass; HTML script-tag demo still works.

## Implementation order

1. Extract internal boot from the current public `init()`.
2. Add `<TestKit />` + types; switch package exports.
3. Wire `scripts/build.mjs` / peers / `files` as needed.
4. Add `examples/react/` and README primary path.
5. Update contracts + `testkit-plan.md` distribution narrative.
6. Tests for mount-once / SSR no-op; regression on existing suite.
